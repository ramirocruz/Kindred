Three roles, not three servers.

A member is anyone admitted. The coordinator/host orders room-state changes. The presenter shares the Drive tab. They can be different people. Everyone can control playback; only the presenter can revoke its tab.

HLD · High-level design

System responsibilities and boundaries

The app is static software downloaded into each browser. There is no Kindred application backend managing membership or storing chat. Hosting, connection infrastructure, room authority and media transport are separate responsibilities.

GitHub Pages & Actions

Pages serves compiled HTML/CSS/JavaScript, extension downloads and these docs. Actions installs dependencies, runs TypeScript/Jest checks, packages the extension and publishes the static build at /Kindred/. Hosting does not carry application chat/calls or own room state. The legacy ChatGPT-hosted app is separate and untouched.

Workflow · Artifact preparation

React browser app

React renders landing/create/join, player controls, participant cards, chat, reactions and dialogs. Vite builds the TypeScript app; Tailwind and existing CSS preserve the legacy UI. Creating or joining makes a browser session and starts PeerJS. UI preferences such as collapsed chat or local mute are not authoritative room changes.

App · WatchRoom

Browser coordinator

The creator admits members and assigns monotonic admission order. It commits and publishes snapshots of membership, encrypted history and presentation state. Members retain copies. An eldest reachable successor must acquire the exclusive stable signaling address before becoming host. A returning creator gets a new identity/order, not restored privilege. Authority is not exclusive playback permission.

BrowserRoom

PeerJS, signaling & ICE

PeerJS wraps browser WebRTC. Signaling exchanges setup metadata and reserves peer IDs. STUN discovers network addresses; TURN may relay encrypted traffic when direct connectivity fails. Current public defaults match the legacy app; explicit self-hosting is optional. Signaling is connection infrastructure, never the room-state service.

Connection policy

Encrypted data channels

Chat, reactions, snapshots and playback commands travel over WebRTC data channels. Invitation-key AES-GCM additionally encrypts application frames. Chat payloads are separately encrypted so replicated history remains ciphertext. Possessing the full invite grants entry; accounts and independent human identity verification are not implemented.

Frames · Chat crypto

Camera/microphone media

Users explicitly join a call with devices off. Device capture then sends tracks through separate PeerJS media calls. Local video is mirrored/muted; outgoing video is unchanged. One incoming stream is rendered per member. Browser speech processing requests echo cancellation, noise suppression and gain control; it does not guarantee noise-free calls.

Call UI · Media transport

GDrive extension & video tab

Only the presenter needs Chrome and the extension. It pins one supported visible video/document and binds it to a room tab. Kindred consumes the tab-capture stream and sends audio/video to guests. Guest controls return to the presenter, where the extension changes the actual Drive video. GDrive uses no debugger and is not a fully clickable iframe.

Worker · Source operations

Memory and lifetime

The latest 100 encrypted messages and committed snapshots live in browser memory. No database, recording service, Firebase, LiveKit or custom room service exists in the active path. If all members leave, the room ends. A MediaStream and source file cannot transfer to a successor; closing the presenter ends its stream even if the room survives.

App, Landing & session.ts — entering a room

Input: display name, room name/reactions or invitation. Output: RoomSession with room/member UUIDs, creator flag, secret and non-extractable CryptoKey. Creators generate a random 256-bit secret. Join validates a UUID invite and canonical 43-character base64url key, rejecting duplicate parameters and non-HTTP(S) URLs. Every join receives a fresh member identity.

App prevents duplicate submissions, updates the URL fragment and mounts WatchRoom. No HTTP room API is called. The key never enters server requests, but the full invite can remain in history/clipboard. Returning hosts cannot automatically reclaim authority. Leaving clears the UI session/fragment.

App · Session

WatchRoom, RoomDivider, RoomChat & GDrivePlayer — UI

WatchRoom consumes RoomConnection rather than owning transport. It renders tabs, dialogs, participant cards, reactions, a docked chat and resizable sidebar. RoomDivider supports pointer/keyboard resize/reset. GDriveVideo attaches one captured MediaStream; GDriveControls commits a timeline seek at interaction end instead of continuously sending intermediate values.

Speaker mute controls local listening, not source pause. Fullscreen retains the sidebar and hover/focus controls. Reaction display and Clear messages are local preferences. Unsupported source submissions remain disabled: a visible tab is not working playback. Chat preserves its draft when delivery is unconfirmed.

Room UI · Player · Chat

useRoomConnection — React/transport composition

Input: RoomSession. Output: members/messages/host/presentation/streams/errors and send/react/control callbacks. It creates BrowserRoom, EncryptedChatInbox and GDriveBridge. Observers update React state; capture commits ownership before enabling outbound screen calls.

A deferred startup avoids reserving peer IDs during StrictMode's discarded mount. Pagehide/unmount cancels startup, disposes decryption, stops capture and closes transport. Back-cache restoration is not guaranteed reconnection. Actual device capture is handled by MediaCall, not this hook.

Hook

BrowserRoom — admission, authority, mesh and dispatch

Owned state: identity Peer, coordinator alias Peer, anchor, authenticated channels, snapshots, timestamps, replay IDs, pending acknowledgements, PeerMedia and PeerScreen. The stable address is kindred-room-<UUID>. Guests connect there for admission and form an authenticated mesh. UUID comparison prevents duplicate connection initiation; admission order chooses successors.

Channel queues serialize encryption/decryption. Frames decrypt and validate before dispatch; malformed/wrong-key frames close the connection. A trusted anchor supplies initial/successor state; host snapshots must obey room/term/sequence rules. The coordinator commits chat/presentation updates and acknowledges them. Drive controls go directly to the presenter, checking request ID/owner/epoch. Timeouts report failure rather than silent success. Close cancels timers/requests and destroys peers/media.

Controller

browser-room-state & gdrive-protocol — pure state contracts

Strict Zod schemas validate members, room snapshots, ciphertext and presentation. Pure helpers admit members, choose the eldest reachable successor, promote only after alias acquisition and compare accepted snapshots. IDs/orders must be unique; host and presenter must be admitted; nextOrder increases monotonically.

Presentation contains owner, public epoch, title, playback and bounded error, never a token/stream. Only its presenter may update/revoke it; another member waits for release. Seek requires a finite nonnegative time. Missing/invalid targets are rejected, never substituted with zero.

Room model · Playback model

room-frame.ts — application control encryption

sealRoomFrame serializes JSON under a 4 MiB limit, creates a UUID and random 12-byte IV, then encrypts with AES-GCM and a 128-bit tag. Additional authenticated data binds version, room, source/channel, destination and frame ID. openRoomFrame validates size/shape, decrypts and parses strict UTF-8 JSON before BrowserRoom validates message kind.

The envelope exposes ID/version/IV/ciphertext, not plaintext. Successful decryption proves shared capability possession, not independent personal identity. A malicious member with the shared key remains trusted. Replay tracking is bounded.

Frame crypto

chat-crypto & EncryptedChatInbox — encrypted history

encryptChat accepts 1–2,000 characters and binds room/member/message IDs with a fresh IV. BrowserRoom checks the authenticated sender, deduplicates and retains 100 encrypted envelopes. Guest sends wait for host confirmation; an unconfirmed request may still have arrived.

Inbox serializes async snapshots/live decryption, deduplicates rendering and suppresses callbacks after disposal. Corrupt ciphertext becomes an unavailable entry without discarding valid history. Clear only hides local IDs. Shared-key encryption has no forward secrecy, automatic rotation or per-person revocation; excluding a saved-link holder requires a new room.

Chat crypto · Inbox

PeerMedia, MediaCall & call-lock — devices and speech

Joining reserves an origin-wide Web Lock and starts an empty stream with devices off. Camera requests ideal 1280×720 at 24 fps, max 30; microphone requests echo cancellation/noise suppression/gain. Off removes/stops tracks. Permission results arriving after leave are stopped.

PeerMedia keeps outgoing/incoming calls separately. It accepts only authenticated, advertised participants while locally joined. Outbound calls are not rendered; one inbound stream per member is. Track replacement closes old outbound calls; stale callbacks cannot overwrite new streams. Leave/unmount releases lock and stops capture. Web Locks are per origin/profile, not global across browsers/devices.

Device UI · Calls · Lock

PeerScreen — movie media transport

Separate screen calls carry {kind:'gdrive',epoch} metadata. Presenters call authenticated members; guests receive without joining a camera call. Receivers check committed owner and epoch before answering. Only the current inbound stream renders.

Presentation changes clear old calls; closed outbound calls can retry during member synchronization. Late joiners learn the presentation before accepting media. Presenter removal clears the stream. Movie audio never passes through microphone speech processing. Snapshots cannot recreate another browser's MediaStream.

Screen transport

GDriveBridge — local capability, capture and polling

The bridge accepts same-window/same-origin messages on kindred-tab-control. A connected-room prepare precedes consuming the extension stream ID with Chrome tab constraints. It creates the public share epoch, commits presentation state and enables screen transport. Token, MediaStream, generation and pending extension requests stay presenter-local.

Control waits up to 8 seconds for actual playback acknowledgement; generation checks reject stale results. Idle state polling every 1.5 seconds updates playback/error snapshots. Reconciliation revokes lost ownership. Stop invalidates requests, stops tracks and sends extension revocation, clearing local screen state even during authority trouble.

Presenter bridge

Extension popup, content bridge, worker & mediaOperation

The popup lists allowed room tabs without exposing invite fragments. The content script maps Chrome runtime messages to same-origin window messages with IDs/timeouts. The worker discovers exactly one visible metadata-ready video in supported Drive/Docs/googleusercontent/youtube.googleapis.com frames and skips foreign/inaccessible frames. It pins source video/document and recipient tab/document, creates a consumer-bound capture ID, and retains token/bindings in chrome.storage.session.

Every command checks token/room/tab/document. mediaOperation runs in the pinned frame and supports state/play/pause/seek only. Pause never writes currentTime. Seek checks finite time, duration and seekable ranges, clamps the endpoint and waits for seeked or explicit failure. Navigation, capture end and tab closure revoke; stop bypasses the slow queue. This is not arbitrary DOM control and uses no debugger.

Popup · Content bridge · Worker · Video operations

peer-config, Vite and Pages packaging — deployment

A blank endpoint omits overrides and uses legacy public PeerJS/ICE defaults. Explicit endpoints require HTTPS outside loopback. Custom ICE/relay-only settings require an endpoint; relay-only requires TURN. VITE_* values are public: never embed a TURN administrator/shared secret.

Local dev uses /; Pages builds use /Kindred/. Downloads respect the base URL. Actions publishes only apps/web/dist with architecture/download assets, after checks succeed. Context, environment files and local receipts are excluded. Self-hosted infrastructure remains an optional future decision, not a hidden fallback.

Follow a request end to end

Create and join

  1. Creator generates IDs/key, starts its identity Peer and claims the stable coordinator alias.
  2. Guest parses the invitation, creates a fresh identity and connects to that address.
  3. Encrypted hello proves capability possession. The coordinator assigns admission order and publishes a snapshot.
  4. Members form authenticated mesh channels. UI displays accepted state rather than dummy participants.

Chat

  1. Composer submits trimmed text; the hook creates an ID and encrypts chat payload/context.
  2. Guest sends it inside an encrypted room frame to the coordinator; a coordinator commits locally.
  3. The coordinator verifies sender, deduplicates, increments sequence and publishes ciphertext history.
  4. Inbox decrypts for display. Confirmation clears the draft; timeout means unconfirmed, not certainly undelivered.

GDrive capture and guest seek

  1. Presenter starts the actual Drive video, opens the extension and chooses a connected room.
  2. Worker pins the video/document and obtains a room-consumer tabCapture stream ID.
  3. GDriveBridge captures, commits a share epoch and starts separate PeerScreen media calls.
  4. Guest sends an authenticated control directly to the presenter. The worker applies it to the pinned source video.
  5. Actual time/duration/paused returns through an owner/epoch/request-checked acknowledgement. Public playback state replicates through the coordinator.
  6. Pixels/audio travel over the media call, not JSON. Chrome suppresses source-tab audio during capture; each member enables one Kindred speaker output.

Host departure and return

  1. Members poll every second. After about 7 seconds without authoritative freshness, they rediscover the stable address.
  2. The eldest reachable member attempts exclusive alias acquisition; timeout alone does not confer authority.
  3. After acquisition it increments term, prunes unreachable members and publishes replicated state.
  4. Stale generations are rejected. Old invites reach the successor; returning creators join at the end as regular members.
  5. A departed presenter's capture ends. A separate surviving presenter can retain its share state if reachable. Arbitrary network-partition consistency is not guaranteed.

Resource and timeout bounds

16 members; 100 retained messages; 2,000 chat characters; 4 MiB serialized room frames; 10,000 received frame IDs per channel and accepted chat IDs per coordinator. Room acknowledgement: 7 seconds. Guest playback: 10 seconds. Extension control: 8 seconds. Native play/seek: 5 seconds. Pending playback capped at 12, worker queue at 20, guest controls at 5 per second per sender. These are protective limits, not measured capacity or latency promises.

Failures, privacy and honest status

Handled in code

Wrong-key/malformed frames, replay IDs, stale snapshots/epochs, cancelled capture, device denial, autoplay blocking and disconnected presenters fail explicitly. Stop/leave close calls, stop tracks and release locks. One corrupt chat entry does not break valid history.

Security limits

No forward secrecy, automatic rotation, independent identity or individual revocation. Invites can remain in history/clipboard. Served JavaScript, devices, extensions and room members remain trusted; members can record. Public infrastructure sees signaling metadata and direct peers may learn IPs.

Design trade-offs

Playback polls currently publish full snapshots with bounded history, not optimized deltas. Background timer throttling can affect 7-second detection; replay caps need long-session testing. Exclusive signaling IDs are not Raft/Byzantine or arbitrary-partition consensus. Latest unreplicated changes can be lost on abrupt departure.

Pending verification/features

Real authenticated Drive capture/guest audio-video, physical-device call quality, TURN-only/difficult-network recovery, dependency/security review, temporary self-hosted TURN credentials, and YouTube/web-video/personal-file/interactive-screen adapters. Fixtures and disabled tabs are not proof of functioning media.

What is verified

Focused Jest coverage exercises invitation parsing, native cryptography, pure authority transitions, simulated encrypted guest controls, source pause/seek, media cleanup, call locks and hosted origin/base-path checks. TypeScript and Pages builds pass. Earlier local browser checks verified room/chat, normal handover and GDrive setup UI—not actual Drive or physical-device media quality.

Run npm run typecheck, npm test and npm run build:pages. CI publishes only after checks succeed. No recording or sensitive-payload logging is enabled by default.

Glossary

WebRTC: browser real-time transport. PeerJS: its wrapper/signaling library. Signaling: setup metadata. STUN: address discovery. TURN: encrypted-traffic relay. Capability: secret granting access. Snapshot: copied committed state. Mesh: members connect to each other. HLD: system responsibilities. LLD: module contracts.
